# E00 — Bridge foundation for the reliable-bridge release

Fixes the connection and command-execution defects that make live editing unreliable, and sets the security posture the release ships with. Findings and verdicts live in [CODE-HEALTH.md](../CODE-HEALTH.md); this file holds the stories.

The first public relaunch promises a **reliable bridge**, not new quality automation. The quality ambition in [VISION.md](../VISION.md) stands; M1–M5 are not prerequisites for promotion.

## Baseline

`package.json` requires Node `>=24`; pin the runtime before running anything, or `npm ci` fails on engine mismatch. On a pinned runtime the offline gate is green: `npm run check` (lint, types, unit tests) and `npm run build` with the committed `dist/index.cjs` unchanged.

Live PowerPoint behaviour and a clean first install are unverified.

## How a story is executed

Each story runs through the engineering loop (E00-00): failing test first, implementation, checks, independent review, live evidence where the story needs a real host, then landing per project policy. A story is done when its acceptance list is literally true — not when the code looks complete.

Two rules apply to every story here:

- Unit tests use a simulated Office host. They prove control flow, never Office behaviour. Anything host-dependent needs live evidence recorded on the PR.
- No story weakens an existing test to go green. A test that pins incidental behaviour gets deleted and replaced with a behaviour assertion.

## Stories

### E00-00 · Engineering loop (prerequisite)

Adapt the Flowbench loop (`$FLOWBENCH/engineering-loop/README.md`) for this repo: issue ownership, worktree isolation, spec → plan → implement → review phases, bounded retries, explicit blocked state, and landing only after checks and an independent review.

Two things do not port as-is:

- `board.sh` writes ownership and lets the latest writer win. Exclusive claiming has to be real, or two sessions can claim one story.
- `agent_review.py` imports flowbench's Python driver. A Node contributor must not need flowbench installed to run a review.

Project-owned values stay here: `npm run check`, `npm run build` + bundle parity, `npm run test:e2e`, the Node 24 pin, live-Office prerequisites, and who may merge.

Acceptance: E00-01 completes every phase through the loop; the reviewer could have rejected it and the approval is recorded; a contributor without flowbench can run the review path.

### E00-01 · One connection per add-in runtime (pilot) — CH03

Target `addin/app.js`. Readiness ordering must not decide how many sockets exist.

Acceptance:

- Office ready before the fallback, after the fallback, and never (plain browser) each produce one connection attempt.
- A second `connect()` while one is connecting or open adds no socket.
- A closed socket still reconnects, with backoff intact.
- Stale timers cannot add a socket after a connection exists.
- Live: cold PowerPoint launch on a disposable deck shows one connected presentation; closing and reopening the taskpane recovers to one.

Regression test: the VM harness that reproduced the double connect, as a vitest case that fails without the fix. `vitest.config.ts` excludes only `node_modules`, `e2e` and `.claude`, so it can live beside the add-in sources or under `server/` — pick one and keep it discoverable.

### E00-02 · Command outcome is never ambiguous — CH01

Target `server/bridge.ts` scheduling and outcome reporting. Reproduced: a caller can be told a command timed out while the mutation runs to completion.

Acceptance:

- Execution timeout excludes time queued behind another command.
- A caller that times out can tell "never started" from "outcome unknown"; an unknown outcome is never retried automatically.
- A late completion is recorded, not silently dropped, and never logs presentation content.
- Waiting is bounded: a lost completion neither frees the slot early (overlapping execution) nor blocks callers forever.
- Reconnect does not imply cancellation — the add-in queue belongs to the page and may still be running.
- Live: a deliberately slow command applies its effect exactly once, and the tool result matches what the deck shows.

This is a relaunch blocker. Changing the error wording alone does not close it.

### E00-03 · Presentation identity across reconnect — CH02

Target identity generation, registration and cleanup (`server/bridge.ts`, `server/index.ts`). Split from E00-01 deliberately: a per-runtime id does not survive taskpane recreation, and evicting a replaced socket can cause reconnect churn.

Acceptance:

- Same runtime reconnecting keeps one entry and one identifier.
- Taskpane recreated on the same deck does not produce a second presentation.
- Save / Save As transitions leave identity and file path correct.
- Two genuinely different decks stay separately addressable.
- Cleanup removes every entry a socket owned; repeated registration is idempotent.
- Live: reconnect, taskpane close/reopen, and save each keep `list_presentations` truthful.

### E00-04 · Connection liveness evidence — CH04

Investigation first. Observe sleep/wake, taskpane recreation and PowerPoint termination: does the socket close, what does the pool hold, what do in-flight commands do, does the add-in recover?

Acceptance: findings recorded with host and OS versions; heartbeat implemented only if it detects an observed failure and does not disconnect a healthy add-in after suspension. "No heartbeat exists" is not a defect on its own.

### E00-05 · WebSocket registration origin — CH16

Order matters: observe real `Origin`/`Host` headers from PowerPoint for Mac and PowerPoint Web (desktop, web, TLS, non-default port) before enforcing anything.

Acceptance:

- Observed host values recorded on the PR.
- A foreign origin cannot register, replace a pool entry, or settle another connection's requests.
- Malformed or missing origin handling is decided from the observed evidence, not assumed.
- Both hosts still connect, including `npm run test:e2e` on the web path.

An origin check is not authentication; CH17's token question stays deferred.

### E00-06 · Bounded HTTP request bodies — CH19

Target `parseJsonBody` (`server/index.ts`). Cap bytes before concatenation and parsing.

Acceptance: the limit is derived from supported requests (base64 `insert_image` is the large case) and stated in the README; an oversize body stops accumulating memory and leaves the server responsive; a near-limit legitimate request still succeeds; chunked bodies and mid-upload disconnects behave.

### E00-07 · Contributor runtime pin

The repo has no `.node-version`, `.nvmrc` or `mise.toml`, so a contributor on Node 22 gets `EBADENGINE` from `npm ci` and a shell that disagrees with CI.

Acceptance: a pin exists, `CONTRIBUTING.md` names it, and a fresh clone reaches a green `npm run check` by following the documented steps only.

### E00-08 · Repository root hygiene

The root carries files that are not part of the project: preview and screenshot PNGs, built `.mcpb` archives, `logs/`, `test-results/`, `playwright-report/`, and `.check-runner.mjs` (a Playwright script driving an unrelated `localhost:5173` app).

Acceptance: strays are removed or ignored, `.gitignore` covers the generated ones, and a fresh clone shows a root that only contains project files.

### E00-09 · Production dependency advisories

CI runs `npm audit --omit=dev --audit-level=high` and it fails on advisories published against the current lockfile — `hono`, `ip-address` and `qs`, all transitive under `@modelcontextprotocol/sdk`. The lockfile has not changed; the advisories are new, so main goes red without a commit. This blocks every PR, including docs.

Acceptance: the audit step passes on a pinned runtime; the upgrade keeps `npm run check` green and `dist/` rebuilt and committed; anything not fixable by a bump is recorded with the reason rather than silenced by lowering `--audit-level`.

## Release gates

The reliable-bridge release ships when:

1. E00-01, E00-02, E00-03 are done with live evidence.
2. E00-05 and E00-06 are done or explicitly deferred with a reason on the issue.
3. `npm run check`, `npm run build` and bundle parity are green.
4. The shipped plugin/MCPB artefacts are installed and exercised, not just the source.
5. The README security section matches the code that ships.
6. A fresh environment reaches its first successful edit with no undocumented step.

## Deferred for this release

Authentication on the MCP HTTP transport (CH17) and an enforced add-in CSP (CH18) stay deferred while the product is loopback-only and single-user. Deferred means unproven-cost, not harmless: revisit both before any non-loopback listener or shared-host support.

Deck-level write limits (CH23), multi-master layout resolution (CH24) and the remaining tool-correctness findings keep their prior evidence and need a failing reproduction before implementation.
